# Contributing to rmctl

Thank you for your interest in contributing to rmctl! This guide will help you get started.

## Prerequisites

- **Go 1.27+** — [download](https://go.dev/dl/)
- **A C23 compiler** — clang 19+ or GCC 13+, for the page and archive commands: rmlines-go and rmdoc-go compile rmlines-lib and rmdoc-lib through cgo. Apple's clang in a current Xcode qualifies; MSVC does not, so on Windows that means clang. Point `CC` at it when the default one is older (`CC=clang-19 make test`). On Linux the renderer also needs the Cairo stack's development packages and PDFium: `make pdfium` fetches PDFium into `.cache/pdfium`, and every Go target builds against it from then on (see [Rendering](docs/rendering.md)). `make build-nocgo` checks the build without cgo, which keeps every command but the page and archive ones. `make rmctl-lite` builds rmctl-lite, rmctl without the renderer (`-tags norender`), into `bin/rmctl`; `make build-lite`, `make golangci-lite` and `make test-lite` build, lint and test every package with that tag, as CI's rmctl-lite job does, and need no Cairo stack or PDFium.
- **Make** — for running project targets
- **Git** — for version control

## Getting Started

1. **Fork** the repository on GitHub.

2. **Clone** your fork:

   ```bash
   git clone https://github.com/<your-username>/rmctl.git
   cd rmctl
   ```

3. **Create a branch** from `develop`:

   ```bash
   git checkout -b feat/my-feature develop
   ```

4. **Make your changes**, then run checks:

   ```bash
   make fmt
   make lint
   make test-all
   ```

5. **Commit** using [Conventional Commits](#commit-messages) and push:

   ```bash
   git push origin feat/my-feature
   ```

6. **Open a Pull Request** against the `develop` branch.

## Branch Naming

Use the following prefixes:

| Prefix | Purpose |
|--------|---------|
| `feat/` | New features |
| `fix/` | Bug fixes |
| `docs/` | Documentation changes |
| `refactor/` | Code refactoring |

## Commit Messages

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>[(<scope>)][!]: <description>

[optional body]

[optional footer(s)]
```

**Types:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `perf`, `build`, `style`, `revert`

**Scope** is optional. When present, it must be listed in [`commit_scopes.txt`](commit_scopes.txt). Never use `root`; omit the scope for repository-wide changes. Use `!` before the colon for a breaking change.

Describe the concrete change and its purpose. Keep the body only when it explains behavior or a decision beyond the subject. Do not include filler, work logs, test results, coverage figures or validation summaries. Do not mention agents or AI assistance, add generation signatures, or add agent co-author trailers. The same format and scope rules apply to PR titles. Merges generated by git (git flow releases and hotfixes) keep git's subject.

Examples:

```
fix(browse): resolve an id prefix that names a folder
feat(write): move a document into the trash
refactor(browse): split the path resolver
test(write): cover a root conflict during mkdir
docs(README): add quick start examples
build(devtools): bump golangci-lint
build(deps): bump golang.org/x/sys from 0.48.0 to 0.49.0
```

Dependabot opens its updates as `build(deps): bump …` (see [`.github/dependabot.yml`](.github/dependabot.yml)); they follow the same rules and get no exemption.

### Automated Validation

- **GitHub Actions** automatically validates all commit messages and PR titles
- **Local validation** can be enabled with: `git config core.hooksPath .githooks`
- Run `bash .github/scripts/validate-commits.sh` to check your commits before pushing
- Run `bash .github/scripts/test-commit-validation.sh` after changing the validator or `commit_scopes.txt`

## Code Style

### Formatting

- Run `make fmt` before committing — this runs `golangci-lint fmt`, so the `gci` sections in `.golangci.yml` order the imports.
- Maximum line length: **156 characters** (enforced by `lll` linter).

### Import Ordering

Imports must follow this order (enforced by `gci` via `.golangci.yml`):

1. Standard library
2. Third-party packages (default)
3. `google.golang.org`
4. `golang.org`
5. `github.com/altessa-s/go-atlas-core`
6. `github.com/altessa-s/go-atlas-net`
7. `github.com/altessa-s/rmctl`
8. `github.com/altessa-s` (other altessa packages)
9. Blank imports
10. Aliases

### Copyright Headers

All `.go` files must include the copyright header. Run `make copyright` to add it automatically.

```go
// Copyright 2026 ALTESSA SOLUTIONS INC.
// Use of this source code is governed by the MIT license that can be found in
// the LICENSE file.
```

## CI checks

CI requires at least 93% total statement coverage on Linux, and every protocol package listed in [`.coverage.yml`](.coverage.yml) must stay at or above its threshold (`make coverage-gate`). Raise these floors as coverage improves; do not lower them to accommodate untested changes. Every protocol scenario needs a negative test alongside the positive one. The full suite runs with the race detector and shuffled test order, and the platform-gated code is cross-compiled for darwin and windows; Windows jobs build the renderer with cgo (MSYS2 CLANG64 on x64, CLANGARM64 on ARM64, and PDFium) and run its tests, with the race detector on x64.

## Tests

| Kind | Files | Run with |
|------|-------|----------|
| Unit | `*_test.go` | `make test`, `make test-race`, `make coverage` |
| Integration | `*_integration_test.go`, first line `//go:build integration` | `make test-integration` |
| Benchmarks | `*_bench_test.go` | `make bench`, `make bench-count`, `make bench-compare` |
| Fuzz | `Fuzz*` targets in `*_test.go` | `make fuzz-seed`, `make fuzz` |

Unit tests never touch the network, the disk outside `t.TempDir()`, or the wall clock: they take the doubles in `internal/porttest`. Integration tests drive the public facade and the real adapters against loopback servers (`httptest`, a real WebSocket server) and temporary directories, on real timers; their lower time bounds are exact and their upper bounds carry slack. Nothing calls remarkable.com. Packages whose tests start goroutines end the test binary with go-atlas-core's leak check, which covers the integration tests too. Benchmarks call `b.ReportAllocs()` and `b.Loop()`, build fixtures outside the loop, and stay fast enough for `make bench-compare`, which the `Benchmarks` workflow runs on every pull request.

## Output formats

Commands never print an answer themselves. They build an `output.Result`: the JSON view (the `--json` shape, held stable by the JSON golden files) and an `output.Doc` of `Table`, `Record`, `Tree` and `Body` blocks made of typed cells (`output.Text`, `ID`, `Size`, `Time`, `Count`, `Bool`, `Path`), and hand it to `env.Emit`; a command whose rows arrive one by one uses `env.Stream`. `cliutil` picks the renderer from `--format`, `--json`, `RMCTL_FORMAT` and the terminal.

A new format is a type with `Render(w io.Writer, r output.Result, s output.Style) error`, registered with `output.Register("name", …)`; it may also implement `output.Streamer` to write streamed rows as they come, or get them as one table at the end. No command changes. The plain format's rules are in the package documentation of `cmd/rmctl/commands/output`; change them only with the Output section of [docs/output.md](docs/output.md#output). Table output is tested with golden files run as a terminal (`clitest.Options{OutTerminal: true}`, `--color never`).

## The cache and new commands

A command says how it may use the cache with `cliutil.WithAccess`: `AccessOffline` for a read that can run from the cache alone, `AccessRead` for a read that needs files the cache does not keep, and nothing (live) for a write or anything only the cloud can answer. Live commands always read the live root and refuse `--offline`; the other two may be answered by a root within the TTL. The cache itself lives in `internal/adapter/indexcache`, as decorators of the driven ports that `internal/wiring` puts in front of the cloud; use cases never see it.

## The Keychain

`internal/adapter/keychain` holds the logic and is tested everywhere against an in-memory Keychain; the calls into Security.framework live in `internal/adapter/keychain/system` (`darwin && cgo`, a stub elsewhere). Its integration tests and the end-to-end Keychain round trip touch the real login Keychain, so they run only with `RMCTL_KEYCHAIN_TESTS=1`, under a service of their own, and remove their items:

```sh
RMCTL_KEYCHAIN_TESTS=1 go test -tags integration -run Keychain ./internal/adapter/keychain/... ./cmd/rmctl/
```

## Fuzzing

`go test ./...` already executes every fuzz target over its `f.Add` seeds, so seeds act as ordinary regression cases and a PR needs nothing extra. Mutation is separate: `make fuzz` walks each target for `FUZZTIME` (`go test -fuzz` accepts one target per package per invocation), and the `Fuzz` workflow does the same nightly with 2m per target, restoring the generated corpus between runs so coverage compounds.

Write a fuzz target when the input is attacker-controlled or there is a property worth stating — a round trip, an allowlist that must hold, an invariant the code documents. "Does not panic" is the floor, not the goal: a target with no assertion passes for the wrong reasons. When a run fails, Go writes the minimized reproducer to the package's `testdata/fuzz/<Target>/`; commit it, so the case is pinned forever in the seed corpus.

## Pull Request Process

1. Ensure `make lint` and `make test-all` pass.
2. Write conventional commit messages: release notes are generated from them by goreleaser at release time, there is no manually maintained `CHANGELOG.md`.
3. Fill out the PR template completely.
4. One approving review is required before merging.
