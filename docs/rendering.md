# Rendering

Back to the [README](../README.md).

`rmctl render <path|id|file.rmdoc>` draws a document, or every document below a folder, the way the tablet shows it — handwriting with its pen textures, typed text, highlights, images and page templates, over the pages of the PDF or EPUB it was made from — through [rmrender-go](https://github.com/altessa-s/rmrender-go), with the fonts and templates it bundles. A cloud document is downloaded and packed as `export` packs it, then drawn; an argument ending with `.rmdoc` that is a local file, such as one `export` or `backup` wrote, is drawn from that archive without the cloud (`./` in front, or the identifier, names a cloud document whose name ends with `.rmdoc`).

| What | Behavior |
|---|---|
| PDF | The whole document, its pages in the document's order. `--mode` matters only for a document made from a PDF: `fresh` (the default) draws a new PDF, keeping links and the outline but not forms or other annotations; `preserving` appends the marks to the original PDF as an incremental update, its bytes untouched, and refuses a document whose pages were moved, added or hidden; `recomposed` writes a new PDF from the original's objects, keeping forms and annotations, and breaks signatures. |
| Page | `--page N` draws page N, from 1, as an image: `--format png` (the default for a page), `jpg` (or `jpeg`) or `svg`; without `--format`, an `-o` ending with `.pdf`, `.png`, `.jpg`, `.jpeg` or `.svg` decides. A PNG or a JPEG is drawn on white; an SVG has no background. `--scale` is a PNG's or a JPEG's pixels per tablet unit: at 1, the default, a page is 1404 pixels wide, as on the tablet's screen. `--quality` is a JPEG's, 1 to 100; 0, the default, is the renderer's, 75. |
| Grain | `--grain mask\|group` is how a PDF draws the grained ink of pencils, brushes and ballpoints. `mask`, the default, draws the grain straight onto the page; `group` draws each grained stroke in a transparency group of its own, as Linux and Windows did before: the PDF is about twice the size, and most viewers draw the strokes' edges lighter. macOS draws both the same, as `mask` does on Linux and Windows. It is for a whole document drawn as a PDF; a page drawn as an image refuses it. |
| Templates | `--no-template` draws the pages without their templates, in any format. |
| Unreadable pages | `--unreadable-pages placeholder\|blank\|strict` is what becomes of a page whose `.rm` file is in the document but does not parse: damaged, or written by a newer tablet than this rmctl reads. `placeholder`, the default, draws "Rendering error" in the middle of the page, dark grey on a light rounded box in Noto Sans, the face of typed text: on a plain white sheet of the page's size, without its template, in a notebook; over the original page in a document made from a PDF. `blank` draws the page as one nobody wrote on: an empty page on its template, or the original page without marks. `strict` fails the drawing, naming the page (`page 3 (<id>) does not parse`, or `is of a format this rmctl does not read`), as rmctl did before the option. Either of the first two draws every other page as it is, counts such pages in the answer as `unreadable_pages` and notes them on standard error. A page the tablet never wrote on has no `.rm` file at all and is always drawn blank, as it always was; a page that fails for want of memory fails whatever the option. It applies to every format: an image of the page carries the label too, which a text recogniser will read, so OCR wants `blank` or `strict`. A document with no such page draws the same whatever the option. |
| Paper | `--paper a4\|letter\|tablet` (A4 by default) is the sheet a notebook page is laid out on; a page of a PDF keeps its own size. |
| Folder | A folder, or `/` for the whole library, draws every document below it as a PDF into a directory, keeping the folder tree: `-o` names the directory, created when missing; without it, a directory named after the folder, or `remarkable` for `/`, in the working directory. Each document becomes `<folder path>/<name>.pdf` (a `.pdf` or `.epub` its name ends with is replaced, and no `-rendered` suffix inside the tree); folders are directories under their safe names, and only those that receive a PDF are created. Two names that collide in one directory, compared without case, are told apart: the first by creation time, then by id, keeps its name, and the later ones get ` (<first 8 characters of the id>)` before `.pdf`, or at the end of a folder's name. `--mode`, `--grain`, `--paper`, `--no-template` and `--unreadable-pages` apply to every document; `--page`, `--scale`, `--quality`, an image `--format` and an `-o` ending with a file extension are refused. Documents in the trash are left out unless `--all` (a folder in the trash named itself keeps its documents). The directory keeps `.rmctl-render.json`, written whole at the end of a run (and before any PDF is drawn when a record no longer holds), which records each PDF's document id, the document's modification time and the options it was drawn with (`--mode`, `--grain`, `--paper`, `--no-template`; a record written before `--grain` existed stands for `mask`). `--incremental` skips a document whose PDF is there with the document's modification time, compared to the second, and whose record names the same document, modified at the same time, drawn with the same options; every PDF written takes the document's time, so a second run draws only what changed, and a run with another `--paper`, `--mode`, `--grain` or `--no-template` draws everything again. A record that is missing or unreadable is no error: every document is drawn, and the record written anew. A PDF that holds an unreadable page (drawn as `--unreadable-pages placeholder` or `blank` says) is not recorded, and its record is dropped, so `--incremental` draws that document again on every run, until its pages read (a later rmctl may read a newer format); the option is therefore no part of the record: no recorded PDF depends on it. A run that stops halfway leaves no PDF recorded under options it was not drawn with. `--jobs N` (`-j`, 4 by default) draws N documents at a time; the downloads overlap, the drawing itself takes turns. A document that fails (a download, a document `preserving` refuses, a drawing) is reported and the others go on; Ctrl-C stops them all. The answer is a row per document — the PDF's path, the document's path, its pages and `rendered`, `unchanged` or `failed` with the error — then the totals; what a document could not keep is noted on standard error after its path. The command fails once the answer is written if any document did. `--all`, `--incremental` and `--jobs` are for a folder alone, and a local `.rmdoc` is always one document. |
| Output | Without `-o`, `<name>-rendered.pdf`, or `<name>-p<N>.png`, `.jpg` or `.svg` for a page, in the working directory, so it never takes the place of the document's own PDF; a directory takes that name inside it. The file appears only once it is whole: it is written beside its destination, as `.<name>.<random>.part`, and renamed into place when the drawing succeeds; a drawing that fails, is refused partway or is stopped leaves nothing behind. A PDF is written into that file as it is drawn rather than held in memory whole, so a long, densely written document needs memory for a page at a time, not for its PDF, and its PDF may be as large as 8 GiB (rmrender-go's 256 MiB bound is for a PDF held in memory). A `preserving` or `recomposed` PDF still reads the original PDF and holds the marks of every page in memory first, and on macOS what CoreGraphics draws of a page (the original's pages, text and images) is held until the last page. A page drawn as an image is drawn whole, then written. The answer is the path, the pages drawn and what could not be kept: blocks of pages that did not parse, pages naming a page the PDF does not have, links a fresh PDF could not carry over, pages that did not parse at all (`unreadable_pages`); each also noted on standard error. |

## open

`rmctl open <path|id|file.rmdoc>` draws a document as `render` does and shows it in the viewer the system opens such files with: `open` on macOS, the shell's open action on Windows (through `ShellExecute`, which takes any file name as it is), `xdg-open` elsewhere. rmctl does not wait for the viewer; a viewer that cannot start is an error once the answer, the path of the file, is written. It takes the options of a single document: `--format`, `--mode`, `--grain`, `--paper`, `--page`, `--scale`, `--quality`, `--no-template`, `--unreadable-pages` and `--id`; a whole PDF by default, the page `--page N` as a PNG. A folder is refused, and so are `-o`, `--all`, `--incremental` and `--jobs`.

The file is kept in the profile's cache, in `<cache>/<profile>/rendered/<key>/<name>-rendered.pdf` (or `<name>-p<N>.png`…): `<key>` is the SHA-256 of what the drawing depends on — the document's record hash, which changes whenever any of its files does (a local archive's path, size and modification time instead), every option, and the version of rmctl. Opening the same document again, unchanged, with the same options, shows that file without drawing or downloading anything; anything else draws it again. The drawings count against the profile's cache budget with its indexes and files, the least recently used evicted first, except the one about to be shown, even when it alone takes more; `debug cache status` counts them as `rendered`, and `debug cache clear` removes them with the rest. With `--no-cache` each open draws into a new directory, `rmctl-open-<random>`, in the system's temporary directory, left for the system to clear, since the viewer may still be reading it when rmctl ends.

```sh
rmctl open /Books/Paper
rmctl open /Notes/Meeting --paper letter --no-template
rmctl open 3f2a --page 3 --format svg
rmctl open ~/rm-backup/3f2a.rmdoc
```

rmctl-lite has `open` too, and it fails as `render` does: a document's original PDF or EPUB is there with `get`, but showing it under `open` would show the document without its ink.

## Builds and platforms

Rendering is in the macOS, Linux and Windows builds of rmctl. **rmctl-lite**, the build without it, leaves the renderer out: its binary is named `rmctl` too and has every other command, and `render` and `open` fail with exit code 1, `rendering is not in rmctl-lite: install rmctl, the full build, for it`. `rmctl version --full` says which build runs: `render yes` or `render no` (`"render": true` or `false` with `--json`). Install one or the other, as in the [README](../README.md#install).

- **macOS** draws with CoreGraphics and CoreText; nothing else is needed.
- **Linux** draws with Cairo, Pango and PDFium. Cairo, Pango, Fontconfig, HarfBuzz and GdkPixbuf come from the system: the binary needs them to start (on Debian or Ubuntu, `libcairo2`, `libpango-1.0-0`, `libpangocairo-1.0-0`, `libfontconfig1`, `libharfbuzz0b` and `libgdk-pixbuf-2.0-0`). PDFium is not packaged by distributions: the release archive carries `libpdfium.so` beside `rmctl`, which finds it in its own directory through its `$ORIGIN` run path, so keep the two together; the Homebrew formula installs both. The licences of PDFium and of the bundled fonts are under `licenses/` in the archive.
- **Windows** draws with Cairo, Pango and PDFium too, on x64 and ARM64, built with [MSYS2](https://www.msys2.org)'s CLANG64 toolchain on x64 and CLANGARM64 on ARM64. They are DLLs, not part of Windows: the release zip carries every one `rmctl.exe` loads beside it — `pdfium.dll`, `libcairo-2.dll`, the Pango, GLib, Fontconfig, HarfBuzz, FreeType and GdkPixbuf DLLs and the C++ runtime they load — and Windows finds them in the program's own directory, so keep the zip's files together; Scoop and winget install them all. Their licences, PDFium's, those of each MSYS2 package and of the bundled fonts, are under `licenses/` in the zip. The first rendering writes the bundled fonts once to `%LOCALAPPDATA%\rmrender\fonts`, where Fontconfig reads them.

Built from source, rendering needs a C23 compiler that reads rmrender-go's sources (clang 19+, GCC 15+ or a current Apple clang) and, on Linux, the Cairo stack's development packages and PDFium. On Linux, from a checkout:

```sh
# Debian or Ubuntu; other distributions name the same libraries their own way
sudo apt-get install clang-19 pkg-config python3 libcairo2-dev libpango1.0-dev \
    libharfbuzz-dev libgdk-pixbuf-2.0-dev libfontconfig1-dev zlib1g-dev
make pdfium              # PDFium, the build rmrender-lib pins, checksum checked, into .cache/pdfium
CC=clang-19 make rmctl   # bin/rmctl, which loads libpdfium.so from .cache/pdfium
```

`make pdfium` takes `PDFIUM_DIR` to put PDFium elsewhere, and `make rmctl` reads it from the same place; keep the directory, since the binary loads `libpdfium.so` from it. A PDFium installed some other way is given through `CGO_CFLAGS` (`-I` its headers) and `CGO_LDFLAGS` (`-L` and a run path to `libpdfium.so`), as `go install` needs too. With Nix, `make pdfium` works in a `nix-shell` that has `go clang pkg-config python3 gnumake git cairo pango fontconfig harfbuzz gdk-pixbuf zlib`; nixpkgs also packages PDFium as `pdfium`, its headers in the `dev` output under `include/public`:

```sh
nix-shell -p go clang pkg-config gnumake git cairo pango fontconfig harfbuzz gdk-pixbuf zlib pdfium
pdfium=$(nix-build '<nixpkgs>' -A pdfium --no-out-link)
export CGO_CFLAGS="-O2 -g -I$(nix-build '<nixpkgs>' -A pdfium.dev --no-out-link)/include/public"
export CGO_LDFLAGS="-L$pdfium/lib -Wl,-rpath,$pdfium/lib"
CC=clang make rmctl
```

CI and the release set PDFium up with `.github/scripts/setup-render-linux.sh`, which writes these variables for a GitHub runner. On Windows it is built in an MSYS2 CLANG64 shell (CLANGARM64 on ARM64), with the toolchain's clang, pkg-config and Cairo stack and the PDFium SDK of the architecture (`win-x64` or `win-arm64`), which `.github/scripts/setup-render-windows.sh` sets up after the packages the CI job installs; the program then needs the toolchain's `bin` and PDFium's `bin` on `PATH`, or their DLLs beside it, which `.github/scripts/bundle-windows-dlls.sh` copies. See rmrender-go's README. Without cgo, or on another system, `render` says it is not available. The bundled fonts add about 27 MB to the binary. `-tags norender` builds rmctl-lite on any of them (`make rmctl-lite`): rmrender-go, its fonts, Cairo, Pango and PDFium are not linked at all, so it needs only the C23 compiler of the page and archive commands.
